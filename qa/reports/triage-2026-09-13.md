#### F-01 — Account takeover by pre-registering someone else's email (`/auth/signup` + `/auth/login`)
- **Severity:** Critical (privacy / account takeover). **Platform:** api. **Status:** VERIFIED (new, found during verification).
- **Root cause:**
  - `app/routers/auth_router.py:50-57`: `signup` creates a password account for any email with no verification.
  - `:60-76`: `login` accepts that password.
  - `:128-136`: `google_auth` finds the existing row by email and logs the real owner into it.
  - There is no rate limiter anywhere in `app/`.
- **Failure scenario:** An attacker signs up as `victim@gmail.com` before the victim joins. The victim later signs in with Google and uses the app. The attacker logs in with their password and reads or writes everything the victim does.
- **Fix:** Delete both routes (neither client calls them; see PM Q1). The schema has no marker for accounts created through `signup`, so removing `login` is what closes the hole.
- **Size:** S · **needs_mobile_build:** no · **needs_pm_decision:** yes (Q1, already open).
- **regression_risk:** No client consumers (dependency-map generated rows 106-107). `tests/` may create users via signup, so grep before deleting.
- **test:** `tests/test_auth.py::TestLegacyPasswordRoutesRemoved::test_signup_404` and `::test_login_404`. Also `test_google_login_existing_email_issues_token_for_that_user` stays green.

#### F-03 — Push notifications cross accounts on a shared device (web + Android)
- **Severity:** Critical (privacy: account A's social activity, with names, is delivered to whoever holds the device next, and B gets nothing). **Platform:** cross-cutting. **Status:** VERIFIED.
- **Root cause:**
  - **api:**
    - `app/routers/push_router.py:39-58`: register looks up the row by `user_id` only. A device token already owned by another user is never reassigned, so one token lives on two users' rows.
    - `app/notifications/router.py` `web_subscribe`: the same problem, keyed on the subscription endpoint.
  - **web:**
    - `context/AuthContext.jsx:21-28` calls `webSubscribe` only when `getSubscription()` is empty. For user B the browser subscription already exists, so B is never registered.
    - `logout()` (`:59-62`) never calls `DELETE /notifications/web-unsubscribe`, which has no consumer.
  - **android:**
    - `src/services/NotificationService.js:13-14,62`: the module-level `lastRegisteredExpoToken` guard skips `POST /push-tokens/` for B.
    - `deregisterPushToken` (`:88-102`) has zero call sites. See `App.js:174-180` `handleLogout`, `SettingsScreen.js:288,297` and `ProfileScreen.js:394`.
- **Failure scenario:** A family shares a phone or laptop. A logs out and B logs in. A keeps receiving B-device pushes about A's account, and B receives no likes, comments or follows.
- **Fix:**
  - api: on register or subscribe, delete the same token or endpoint from other users.
  - web: always call `webSubscribe` when permission is granted, and unsubscribe on logout.
  - android: reset the guard and call `deregisterPushToken` on logout and on account delete.
- **Size:** M · **needs_mobile_build:** yes (Android half; api + web ship in 4A) · **needs_pm_decision:** no.
- **regression_risk:** The `pushtoken` table contract (every query filters `token_type`), `fire_event()`, `admin_broadcast`, and `tests/test_push_tokens.py`.
- **test:**
  - `tests/test_push_tokens.py::test_register_token_owned_by_other_user_moves_row`
  - `tests/test_push_tokens.py::test_web_subscribe_same_endpoint_moves_between_users`
  - Live, web: reader enables push → logout → friend logs in on the same browser profile → reader likes friend's own note → only the friend's browser shows the push.
