## Contracts that must not drift

### Userbook shape  ⚠️ 13 consuming files
Returned by `GET /userbooks/`, `GET /userbooks/{id}`, `GET /userbooks/user/{id}` and `POST /books/add-to-library`. It is a flat object with a nested `book`:
```
{ id, user_id, book_id, status, current_page, rating, format, ownership_status, created_at, updated_at,
  book: { id, title, author, description, total_pages, cover_url, google_books_id } }
```
`PUT /userbooks/{id}/progress` and `PATCH /userbooks/{id}` return minimal dicts `{id, status, current_page, rating, updated_at[, book_total_pages]}`, never a raw SQLModel.

**Dedup.** Server-side dedup in `add-to-library` matches `google_books_id`, then `isbn` (`books_router.py:47-51`). **(4A — in build)** It will match an optional `book_id` (a local Book id) first. Every book object a client can pass to BookPreviewModal/Screen must therefore carry `google_books_id` + `isbn` + `total_pages`. Today these do not, and adding from them creates a duplicate Book (F-07):
- `/books/recommendations`
- `/userbooks/friends/currently-reading` `.book`
- the note card `.book`
- `GET /groups/{id}` `.current_book`
- web `LibraryPage.jsx:192-202` `handleAdd` (omits `google_books_id`)

4A adds the keys to all of these.

**(4A — in build) Request and data rules:**
- `PATCH /userbooks/{id}` takes a Pydantic model (F-52). Its response is unchanged.

  | Field | Allowed values |
  |---|---|
  | `status` | `to-read`, `reading`, `finished` |
  | `rating` | integer 0–5 or null; 0 or null clears |
  | `current_page` | ≥ 0 or null |
  | `total_pages` | ≥ 1 |
  | `format` | `hardcover`, `paperback`, `ebook`, `kindle`, `pdf`, `audiobook` |
  | `ownership_status` | `owned`, `borrowed`, `loaned` |

  Extra keys are ignored; anything else returns 422.
- `DELETE /userbooks/{id}` deletes the userbook's `reading_activity` rows and nulls `group_post.userbook_id`. Today these violate the foreign key, so the delete returns 500 for any book that was ever progressed (F-50).
- `userbook(user_id, book_id)` is UNIQUE (index `uq_userbook_user_book`, F-53). A losing duplicate insert returns the normal 400.

**Why this matters.** On 2026-05-04, `add-to-library` returned `{message, book, userbook}`; BookPreviewScreen stored the wrapper, and `PATCH /userbooks/undefined` returned 422. The same day, `handleRating` used `PUT /progress` with `{rating}`, which set `current_page=0` and reset every rated book to `to-read`. The DB repair for that bug is `context/repairs/2026-09-rating-reset-repair.sql` (F-16, PM-run). **Rating goes through PATCH; page progress through PUT.**

### `GET /profile/me`  ⚠️ 10 consuming files
- `stats` carries both snake_case and camelCase keys (`total_books`/`totalBooks`, `to_read`/`toRead`, `total_pages_read`/`totalPagesRead`) on purpose. Mobile reads camel, web reads snake; removing either breaks a shipped app build.
- `GET /profile/{id}` returns `stats: null, locked: true` for a private profile the caller does not follow. `follows_you` and `yearly_goal` were added 2026-05-04 for the Follow-Back label.
- **(4D — designed, not built)** On web, `/profile/me` stops being a gate. Signed-in pages mount while it is in flight, and `useAuth().user` is `null` until it answers.
  - A page must never build a request from `useAuth().user`. `ProfilePage` switches from `/userbooks/user/{me}` to `/userbooks/`.
  - Identity-dependent UI must treat `null` as "not known yet".
  - Only `/admin` and `/onboarding` still wait.
  - The response shape is unchanged. See `features/maintenance/sprint-4d-page-speed/architecture.md`. After the build, run `python scripts/gen_dependency_map.py`.
- `PUT /profile/me` applies a field only when it is not null, so a client cannot clear `yearly_goal` by sending null. Both Settings screens do send null when the field is emptied (F-18). **(4A — in build)** A `yearly_goal` key that is sent is applied, and null or 0 clears it. Other fields keep their not-null semantics.

### Note card shape — `GET /notes/feed`, `/friends-feed`, `/me`, `/user/{id}`
```
{id, user_id, text, emotion, page_number, chapter, quote, image_url, is_public, created_at(Z), likes_count,
 comments_count, liked_by_me, user_has_liked, user:{id,name,username,profile_picture}, book:{id,title,author,cover_url}}
```
- `liked_by_me` and `user_has_liked` are duplicates kept for old clients.
- `/me` also has `updated_at`.
- `/user/{id}`: `user_id` is padded to `null` by `NoteOutSchema` and `user` is only `{id, name}`. It **does** return real like state: `likes_count`, plus the viewer's `liked_by_me`/`user_has_liked` since **F-63 (2026-09-18)**. Before that the like keys were the schema default `False` for every viewer, and this map recorded it as "omits the like keys; defaults filled", which led tests.md §9 R-03 to assert the bug as the contract. **Both clients read these keys here:** web `UserProfilePage` uses `liked_by_me`, Android `UserProfileScreen` uses `user_has_liked`. **Lesson:** a key filled by a default is still a contract. Record what its value *means*, not just whether it is present.
- `/friends-feed` `user` adds `is_mutual`.
- `GET /notes/feed` is **optional-auth**, so anonymous callers get it. It excludes `is_private_profile` authors in `crud.get_notes_feed`, but not review accounts (F-09, not approved).
- `.book` lacks `google_books_id`/`isbn`/`total_pages` today.
- All five note serializers (including `/userbook/{id}`) lazy-load user, userbook and book per note: 114 queries for 50 notes (F-08).

**(4A — in build):**
- `book` gains `google_books_id`, `isbn` and `total_pages` on the four endpoints above (`/userbook/{id}` keeps `{id,title,author}`).
- Relations are batch-loaded with 3 `IN()` queries, so query count is independent of page size.
- `limit` is validated 1..200 (F-51).
- `POST /notes/` without `is_public` creates a **private** note, and `PUT /notes/{id}` without `is_public` keeps visibility (F-17). Android 2.2.1 `BookDetailScreen.js:172` omits the field, so those notes become private.
- Like, comment and comment-list return 404 for another user's private note, and 403 for a private-profile author the caller does not follow (F-02).
- `like(note_id, user_id)` is UNIQUE (`uq_like_note_user`).

### `app/deps.py :: get_current_user`
Every authenticated route uses it. It also writes `user.last_active` once per day, which the streak-reminder scheduler reads. Changing it touches every request and the reminder logic. It costs 1 SELECT (+1 UPDATE per user per day), which counts in any query-count test.

### Auth — `/auth/*` + `GET /version`
**`POST /auth/signup` and `POST /auth/login`** are unauthenticated and unused by clients, with no email verification and no rate limit. Combined with `/auth/google`'s find-by-email, they allow account takeover (F-01). **(4A — in build)** Both are deleted; PM approved 2026-09-13. The live auth routes are then:
- `POST /auth/google`
- `POST /auth/review-login`
- `POST /auth/delete-account` (public form)
- `POST /auth/delete-account/me`

The generated map shows `⚠️` on `review-login` and `/version`. That is deliberate, not a gap.

**`POST /auth/review-login`:**
- It is **gated by an env allowlist + a shared secret, and returns 404 when unconfigured.** With `REVIEW_LOGIN_SECRET` or `REVIEW_LOGIN_EMAILS` unset, it behaves as if the route does not exist. That is the state of local dev, the test suite and any fork.
- When configured, it accepts only addresses that are in `REVIEW_LOGIN_EMAILS` (comma-separated, trimmed, case-insensitive) **and** end in `@trackmyread.com`. Everything else gets an identical 401, so the allowlist cannot be enumerated.
- The secret is compared with `hmac.compare_digest`.
- It returns the **same body as `POST /auth/google`**: `{access_token, is_new, user:{id,name,email}}`.
- It creates accounts the same way (`secrets.token_urlsafe(32)` → `auth.hash_password` → `crud.create_user`). Review accounts are therefore ordinary users, and every downstream contract applies unchanged.
- No client calls it. The token is used by `curl`, by `scripts/seed_review_accounts.py`, and by pasting it into `localStorage.bt_token` for web screenshots.
- Both env vars are read **inside the request**, never at import time.

**`GET /version`:**
- It returns exactly `{commit, service, branch}`, taken from `RENDER_GIT_COMMIT` / `RENDER_SERVICE_NAME` / `RENDER_GIT_BRANCH`; all are `null` off Render.
- It is unauthenticated on purpose. **Never add anything else to this response.**
- It lives in `app/routers/meta_router.py` with **no `prefix=`**, not in `main.py`: `scripts/gen_dependency_map.py` only matches `@router.<verb>(`. See `features/auth/review-login/decisions/ADR-001-version-route-placement.md`.

### `app/main.py` middleware stack  (4A — in build)
The order, from innermost user middleware outward:
1. `CatchUnhandledErrorsMiddleware` turns any unhandled exception into `500 {"detail": "Internal Server Error"}` **inside** CORS. It logs to `app.errors` with method and path only (F-58). Today a 500 has no `Access-Control-Allow-Origin`, so browsers report `net::ERR_FAILED` and cannot read the error.
2. `CORSMiddleware`: the explicit origin list, unchanged.
3. `SecurityHeadersMiddleware` adds `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and `Strict-Transport-Security: max-age=31536000; includeSubDomains` to every response, preflights included (F-56).

Starlette `add_middleware` puts each new middleware outside the previous ones, so **registration order in `main.py` is load-bearing**. Tests: `tests/test_security_headers.py`.

### `app/notifications/dispatcher.py :: fire_event()` + `config.py`
**The only push path** (Expo + web push + NotificationLog). Its callers:
- `follow_router`
- `likes_comments`
- `books_router`
- `userbooks_router` (×4 sites)
- `groups_router`: invite, join request, approve, reject
- `notifications/router`: admin test
- `notifications/scheduler.py`: `reading_streak_reminder`, `actor_id=0`

**Cost per recipient:** `db.get(User)` for prefs, a daily-cap query when configured, expo and web token queries, the Expo and web-push HTTP calls, and a log row; one commit at the end. **(4A — in build) F-59:** every call made during a request is scheduled with FastAPI `BackgroundTasks` and runs after the response. So do `fire_group_activity*`. Arguments are captured at request time.
- **It relies on FastAPI 0.95 running background tasks before `yield`-dependency exit** (the request `db` is still open).
- **Any FastAPI upgrade to ≥ 0.106 must give those tasks their own Session.**
- `admin_router.broadcast_push_notification`, the admin test route and the scheduler stay synchronous.

**One deliberate exception:** `admin_router.broadcast_push_notification` fires `event_type="admin_broadcast"` by calling `send_expo_push` + `send_web_push` per user and writing its own `NotificationLog` row (`actor_id=<admin id>`). It bypasses `fire_event` because the admin supplies `title`/`body` at call time, and an operational announcement is not gated on per-user prefs, so `admin_broadcast` is absent from `USER_PREF_KEYS`. It is registered in `config.py` only for the admin events screen and kill switch. **(4A — in build)** `GET /admin/stats` gains `push_subscribed_users` (distinct users with any push token), the broadcast audience, which the web confirm dialog shows.

**Pref keys** shared with both Settings screens: `new_follower · post_liked · post_commented · book_completed · reading_streak_reminder · group_invite · group_join_request` (`book_added` follows `book_completed`).
- `PATCH /notifications/prefs` **returns 500 in production for every body.** `prefs.model_dump()` is Pydantic v2, and the stack is Pydantic 1.10 on FastAPI 0.95 (F-49). The code also replaces the stored dict, so omitted keys would reset to `true`; mobile sends partial bodies (F-06).
- **(4A — in build)** `.dict(exclude_unset=True)` is merged into the stored dict, and the response is the 7-key dict. **Rule: the app is on Pydantic v1. Never use `model_dump`, `model_validate` or `model_fields_set`.** `tests/test_pydantic_v1_compat.py` guards this.

**Deep links:**
- `group_join_approved`, `group_join_rejected` and `admin_broadcast` have no deep-link handling on either client.
- Web `public/sw-push.js` ignores `notification.data` and always opens `/` (F-22).
- **(4A — in build, web)** Approved → `/groups/{group_id}`; rejected → `/groups`; broadcast → `/notifications`. The same mapping is in `NotificationsPage.getDestination` and `sw-push.js :: urlForNotification`; keep them in sync. Android gets it in 4B.
- Push `data` is `{type, actor_id, **extra}`; group events include `group_id`.

**(4A — in build) F-23:** `POST /notifications/{id}/read` → `{id, is_read: true}`. It is owner-checked, returns 404 for other users' or unknown ids, and is idempotent. Consumers: web `NotificationsPage.jsx`, Android 4B `NotificationsScreen.js`.

**Template trap:** `_render_template` returns the raw template on a missing `{placeholder}`, with no error. Every `extra` must supply every placeholder in the config entry.

### `pushtoken` table
- **Channels:** one table, two channels: `token_type='expo'` (mobile) and `'web'` (PWA). Any query on this table must filter `token_type`.
- **Today:** register (`push_router.py:39-58`) and `web-subscribe` key on `user_id` only. A token already owned by another user is not reassigned, so a shared device delivers A's pushes after B logs in (F-03).
  - `web-subscribe` deletes **all** of the user's web rows before inserting.
  - Mobile `deregisterPushToken` has zero call sites (fixed in 4B).
  - `DELETE /notifications/web-unsubscribe` has zero consumers.
- **(4A — in build)** `POST /push-tokens/` deletes any `expo` row with the same token for another user.
- **(4A — in build)** `POST /notifications/web-subscribe`:
  - It requires `subscription.endpoint` (400 otherwise).
  - It deletes every `web` row whose stored subscription has that endpoint, for any user, matched on `endpoint` and not on the JSON string.
  - It keeps the caller's rows for other endpoints, so multi-browser users get pushes in each browser.
- **(4A — in build)** `DELETE /notifications/web-unsubscribe` removes only the caller's row for that endpoint. Web calls it on logout with the pre-logout token. Web registers on load only when `Notification.permission === 'granted'` (F-27).

### `follow` / `like` / `userbook` uniqueness  (4A — in build)
**Today:** no unique constraints, so concurrent requests create duplicates (F-53).

**Migration:** appended to `context/supabase_migration.sql`. The PM runs it before the 4A backend deploy:
1. STEP 1: read-only counts.
2. STEP 2: dedupe, keeping the lowest id. Dependents are repointed: `note`, `reading_activity`, `group_post`, `journal`. Backup tables are `dedupe_20260913_*`.
3. STEP 3: `CREATE UNIQUE INDEX` `uq_userbook_user_book`, `uq_like_note_user`, `uq_follow_pair`.

- like: `{"message": "Already liked"}`
- follow: 400 `"Already following"`

`import_router` is not guarded (residual).

### `context/supabase_migration.sql` ↔ `app/models.py`
- **Rule:** every column in models.py must have an `ADD COLUMN IF NOT EXISTS` here, run in Supabase **before** the model ships. Pushing first crashes every query on that table (April 2026 login outage).
- **Constraints:** a unique index is different. A model-only `UniqueConstraint` does not crash queries, but it protects nothing until the index exists. Run the index SQL first anyway.
- **One-off data repairs** live in `context/repairs/*.sql`, run by the PM in parts. Read-only part (a) first.

### Mobile `App.js :: preloadData()` → PreloadContext
- **What it runs:** 9 parallel requests (keys `profile, library, feed, insights, activity, notes, groups, pendingGroups`, plus the unread count), then `_silentCoverFix()` on every launch.
- **What depends on it:** these seed the Feed / Library / Insights / Groups / Profile screens. A screen that should open instantly needs a request here, and changing a response shape here changes the first render of every tab.

### `googlebooks_router` — `/api/googlebooks/search`, `/book/{id}`, `normalize_google_cover_url`
**`normalize_google_cover_url`** is imported by `userbooks_router`; cover URLs are normalised on read, not on write.

**Client mapping:**
- Web maps `google_id → google_books_id`, `authors[] → author` and `isbn_13|isbn_10 → isbn` in `api.js searchGoogleBooks`.
- Mobile `booksAPI.search` returns the raw response, and mapping is per screen. `LibraryScreen` does it; `AppTour.js:187` reads a nonexistent `books` key (F-12, 4B).

**Known defects today:**
- The search route builds a frontcover URL from `google_id` even when Google has no image, which yields Google's "image not available" placeholder (F-19).

- Both routes are **unauthenticated** (F-29).

**(4A — in build):**
- **F-19:** `cover_url` is null when the volume has no `imageLinks`. Stored placeholder rows are not cleaned (PM: not approved).
- **F-54:** `start_index` ≥ 1000 returns an empty page, and Google failures return 502.
- **F-29 (PM-modified): both routes stay public but are quota-limited.**

  - It is keyed by a per-process salted SHA-256 of the right-most `X-Forwarded-For` entry, the one Render's proxy appends; a forged left-most value is ignored (else the client host). It is held in memory only, resets on Render restart or sleep, and the raw IP is never stored or logged.
  - The 3rd call gets `401 {"detail": {"code": "login_required", "message": "Log in to keep searching"}}`.
  - Authenticated callers are unlimited. Every current consumer is authenticated.
  - The generated table will keep `⚠️ NONE` for these rows. That is correct: the protection is the quota, not auth.
