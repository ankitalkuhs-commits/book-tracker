## How to read this plan

- Cases are grouped by the **work packages in architecture.md** — P1 the column and the guard, P2 verification and the linking rule, P3 revocation on deletion, P4 the iOS client — then by requirement. A Builder reads section 0, their own section, and the gates.
- **Ids.** The architecture's ids are kept unchanged where they exist: `B-01..B-13` (verification), `B-20..B-34` (linking), `B-40..B-44` (revocation), `A-01..A-07` (iOS client), `P-01..P-10` (production). New ones continue each series (`B-35`, `B-37`, `A-08`) or take a letter suffix (`B-23a`). Production checks are renumbered `P-4G-01..` so they do not collide with 4C's `P-4C-*` or 4F's `P-4F-*` in the run ledger; the architecture's `P-01..P-10` map onto them in order and the mapping is in section 7. Other prefixes:
  - `ST-4G`: static command, run from the worktree root.
  - `RG-4G`: regression.
  - `G-4G`: gate.
  - `D-4G`: a device/TestFlight check a human performs.
  - `MUT-4G`: a row in the mutation-proof table (section 9).
- **Severity:** Critical = authentication, the linking rule, account deletion, or a reader silently losing their library. Major = a branch or a client affordance dead, or a deploy-order guard missing. Minor = cosmetic or defensive. **Every authentication and every linking case is Critical and is never downgraded.**
- **Priority:** P0 ship blocker · P1 fix within the sprint · P2 nice to have.
- **Mutation testing is the acceptance rule.** Every case names the **one-line change to named product code** that must turn it red, and the first failure line to expect. Section 9 is the table the Builders fill in. **A test whose mutation stays green is not coverage: the merge is blocked until the test is fixed or the case is deleted.** A case for which no mutation could be named does not appear here — that is why several ideas from the architecture's draft table have been split (B-02a, B-23a, B-24b, B-10a), tightened (A-02), or moved out of the automated suite entirely and into section 7 or section 10.
- **This sprint's single most important mutation is `bool(claims.get("email_verified"))`.** `email_verified` arrives from Apple as the **string** `"false"` and `python-jose` passes strings through uncoerced, so the naive truth test is **true for `"false"`** and links an unverified email onto an existing reader's row (F7, an account takeover). That naive check is MUT-4G-23 and it must turn **B-23** red. Every claim-shape case is parametrised over **both** the boolean and the string forms, in both directions, with the list length asserted first.
- "Expected" is what spec.md and pm-decisions.md promise as amended by section 0, not what the code does today.
- Where a case says "unchanged", the assertion is against a **captured before value**, not a literal typed into the test (4E's section 2.5 rule).

### Non-vacuity rules — carried forward from 4C/4F, extended for 4G

Binding on every case in this plan. Rules 1-8 are 4F's, unchanged. Rules 9-12 are new this sprint, each for a defect this project has actually shipped in the last three weeks.

1. **Every injection asserts a control.** A test that makes a token invalid also exercises a valid token in the same test. A 401 case with no 200 control cannot tell "bad tokens are rejected" from "every token is rejected".
2. **Every enumeration first proves its inventory is complete.** A parametrised walk asserts the list it walks **equals** the full set discovered from `app.routes` / the file, before it checks anything.
3. **Every detector runs against a synthetic positive.** A rule that greps, walks an AST or scans a log proves on a deliberately-failing snippet that it reports a hit, in the same test.
4. **A walker that finds zero sites fails.** Every enumerating test asserts `found == EXPECTED_N` with `EXPECTED_N` written out in this plan, **before** the per-site assertions.
5. **Every new test file opens with an import guard** at module scope, so a missing or renamed symbol is one loud failure and never N silent skips.
6. **No gate counts a `-k` filter's output; every gate counts the whole file or the whole suite, exactly.** Mutation rows name a test by its **full node id**, never by a substring. *(The defect: a `pytest -k book_id` filter over-matched `userbook_id`.)*
7. **A file that fails to load is a count change, not one failure.** Gates compare `# tests`, `# pass` **and** `# fail` exactly.
8. **A test that can pass against unbuilt code is a defect.** Every case names the symbol whose absence must make it fail loudly rather than skip (K-07).
9. **A parametrised claim-shape list asserts its own length, and it is asserted in BOTH directions.** A list of "not verified" shapes with no matching list of "verified" shapes cannot tell "the coercion is strict" from "nothing ever links". B-23 (9 shapes that must **not** link) is paired with B-23a (4 shapes that **must** link); B-24 (4 relay shapes that must **not** link) is paired with B-24b (5 non-relay shapes that **must**). Each of the four asserts `len(SHAPES) == <literal>` first. *(The defect this exists for: a guard whose diff range was empty after a merge, so three cases passed while asserting nothing.)*
10. **A test that mints its own Apple token and verifies it with our own verifier proves our verifier, not Apple.** Every case in section 3.1 says, in its own row, what it establishes and what it does not. The only thing in CI that touches Apple's real bytes is **B-02a**, which parses a checked-in snapshot of Apple's public JWKS document. Nothing in CI proves Apple signs what we expect; R-15 item 1 is the substitute and section 10 item 1 says so. *(The defect: a test asserting `valid_zone("localtime") is None` passed on Windows because the tz wheel had no such key — nothing was exercised — while production on Linux had a live bug.)*
11. **A platform-conditional client case must force the condition, not assume the platform.** A-01 forces `isAvailableAsync` to resolve **false** and asserts one button; A-02 forces it **true** and asserts two. A test that reads `Platform.OS` from the Node runner is testing Node. *(Same family as rule 10: the environment answered the question instead of the product.)*
12. **A size or layout claim is computed from the product's own tokens, or it is not asserted at all.** A-02 derives the expected Apple-button height from `theme.js`'s `type.title.lineHeight` and `LoginScreen.js`'s `googleBtn.paddingVertical`/`borderWidth`, so changing either turns it red; it does **not** compare against a literal `48`. Claims that cannot be derived — "above the fold", "App Review will judge these equivalent" — are **not** automated; they are D-4G rows. *(The defect: a Playwright harness measured a different checkout because a dev server silently took another port — the harness believed a number it had not established.)*

## 10. What this plan does NOT cover

Stated plainly, because a gap nobody names becomes a gap somebody assumes was covered.

1. **No iOS device, no simulator, no TestFlight build — and this sprint does not produce one** (K-10). `eas.json` has no `ios` profile and no package adds one, so at the end of this sprint the API half is fully proved and the client half is proved **only as source shape**. Every A-* case is an AST or text assertion over committed source: it proves an `AppleAuthenticationButton` element sits above the Google one with a computed height, guarded by `isAvailableAsync()`. It does **not** prove the button renders, that the sheet opens, that it returns an `identityToken`, or that the token's `aud` is our bundle id. **Substitute proof:** D-4G-01, by hand on the first TestFlight build. **What remains genuinely unproven until then:** everything in P-4G-05..09 and D-4G-01..03 — and since the build cannot be made from this repo as it stands, that is not a deferred check but a blocked one. Say so in the done checklist.
2. **No registered bundle id, so nothing proves the `aud` we verify is the `aud` Apple will send.** `app.json:30` is `com.bookpulse.mobile` and pm-decisions E-2 keeps it; no Apple Developer identifier exists, and the Sign in with Apple capability is per-identifier and is the step most often forgotten (architecture E-2 item 2). **Substitute proof:** B-06 proves the check is enforced and configurable, and R-02 makes `APPLE_AUDIENCES` an env var so a wrong value is a Render edit and not a deploy. **Unproven until TestFlight:** that the registered id, the App Store Connect record, `APPLE_AUDIENCES` and `app.json` all carry the same string. A single one left behind is a 401 on every sign-in.
3. **No real Apple account, so no case proves Apple's claim shapes.** Which of `bool` and `str` Apple sends for `email_verified` and `is_private_email`, and whether `email` is present on the second sign-in, vary by Apple ID type and are not contractually fixed. **Substitute proof:** the suite parametrises **both** shapes in **both** directions (B-23/B-23a, B-24/B-24b) and the design is correct for either, so the device check is a confirmation and not the proof — which is the right way round: a design that needed the device to be correct would be the defect. The one thing in CI that touches Apple's real bytes is **B-02a**, the checked-in public JWKS snapshot, and it proves only that the document parses and that our `kid` reader finds every key. **Unproven until TestFlight:** that Apple signs RS256 with a key in that document, which no public artefact can establish.
4. **No live `auth/revoke`.** B-40 proves the request shape and that the ES256 `client_secret` verifies against the right key with the right `iss`/`sub`/`aud`/`exp`; the HTTP call is mocked in every case. **Substitute proof:** a one-time manual check with a throwaway Apple ID, P-4G-08 / done-checklist 11. And under pm-decisions E-4 the live call may ship **knowingly inert** until the PM creates the `.p8`, in which case B-42's fourth parameter (the unset key) is the only thing that runs in production and the revocation is a recorded submission risk, not an oversight.
5. **F8 is not tested and is not fixed** (K-09). `/auth/google` never reads Google's `email_verified` (`auth_router.py:75-77`) and matches on email (`:83`), so an attacker who signs up with a victim's address first gets the victim logged into their row. It is the mirror image of branch 3, it exists today, it is not created by this sprint, and pm-decisions E-1 rules it out of scope with an instruction to log it. **No case asserts anything about it.** A reader could be taken over through that hole while every test in this document passes.
6. **Branch 5's safety rests on DNS, which no test touches** (K-06). `users.noreply.trackmyread.com` must route no mail, or Apple could in principle verify a synthesised address and branch 3 could match a branch-5 row. **Substitute proof:** P-4G-11, a one-off `MX` lookup. Nothing re-runs it.
7. **No concurrency test and no PostgreSQL in the automated suite.** B-29 asserts that a duplicate `apple_sub` produces one row and a deterministic error, against **SQLite's** unique-index `IntegrityError`, not two simultaneous requests against PostgreSQL. 4C built `qa/pg_4c_migration.py` for exactly this gap and this sprint does not extend it, because the SQL is additive and re-runnable and the `IntegrityError`-to-HTTP shape is already proved in production by `follow_router.py:39-44`. If the PM wants it, it is a half-day: a `qa/pg_4g_apple_sub.py` in the same shape.
8. **The Apple button's accessibility is untested** (K-17). `a11yTouchables.test.mjs` cannot see `AppleAuthenticationButton` — it is not in `TOUCHABLE_TAGS` — so a green a11y sweep says nothing about it. Apple's native view carries its own label and we do not control it. Nothing here proves the pre-tap message (A-10) is read out, is legible at the smallest text size, or is not clipped.
9. **"Equivalent prominence" as App Review judges it is a human judgement, and "above the fold" is probably already false** (K-03, Q-2). A-02 asserts order, width, radius and a height derived from the product's own tokens, which makes a regression catchable. It cannot assert the 3pt border question, Apple's native intrinsic metrics, or anything about the viewport. **Substitute proof:** D-4G-02's measured screenshot, which is also the argument to the reviewer. If the layout is not changed, that screenshot is likely to show the two buttons below the fold on a small device, and this plan predicts it rather than discovering it.
10. **Nothing proves App Review passes.** It is the success metric, not a test, and it is binary. The two things that fail a submission here are a 4.8 rejection (addressed by R-09 and, under pm-decisions E-6, trivially satisfied because iOS uses no third-party login at all) and a 5.1.1(v) rejection (addressed by R-12's verification and R-13's revocation). Neither is testable and both are checked by a human in the App Store Connect flow.
11. **The PM SQL is proved as text, not as an executed migration.** B-37 parses `context/PM_SQL_QUEUE.md`. It cannot prove the PM ran it, that PostgreSQL accepted it, or that the unique index was created rather than skipped by an `IF NOT EXISTS` against a pre-existing non-unique index of the same name. P-4G-01, P-4G-02 and G-4G-09 are the only proof and they are the PM's output, pasted back.
