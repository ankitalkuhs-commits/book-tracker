## Analysis (orchestrator, 2026-09-13)

**Network vs database.** `/` and `/version` touch no database and answer in **~245 ms p50** — that is Pune → Render. Endpoints that run 2 queries (`/notifications/unread-count`) take **~956 ms**, 3 queries (`/userbooks/`) **~1,131 ms**, 5 queries (`/profile/me`) **~1,481 ms**. So each production DB round-trip costs roughly **150–250 ms** — the Render service and the Supabase database are almost certainly in different regions (same symptom School ERP had). Regions are not visible from here; needs a look at the Render service region and the Supabase project region.

**N+1 on the feeds (proven locally).** SQL queries per request, SQLite in-memory, 10 users / 50 public notes (count is independent of latency):

| queries | endpoint | prod p50 |
|---:|---|---:|
| 114 | `GET /notes/feed` (50 notes) | **9,240 ms** |
| 106 | `GET /notes/friends-feed` (45 notes) | 2,709 ms (2 notes in prod) |
| 15 | `GET /notes/me` (5 notes) | 2,183 ms |
| 15 | `GET /notes/user/{id}` (5 notes) | 2,185 ms |
| 10 | `GET /books/recommendations` | 2,718 ms |
| 5 | `GET /profile/me` | 1,481 ms |
| 4 | `GET /reading-activity/insights` | 1,287 ms |
| 3–4 | `/users/following`, `/users/search`, `/users/{id}/stats`, `/userbooks/` | 1,131–2,084 ms |
| 2 | `/follow/following`, `/groups/my`, `/notifications/unread-count` | 956–2,167 ms |

The note serializers touch `n.user`, `n.userbook` and `n.userbook.book` per note (lazy loads), so a 50-note feed issues ~2 extra queries per note. At ~80 ms/query that is the 9.2 s Home page load. Fix: load users/userbooks/books for the page in batched `IN (...)` queries (or `selectinload`) — expected ~5–7 queries regardless of page size.

**Concurrency** (5 parallel): no errors, no queueing growth — the feed is slow per request, not under load.

**Other:** `POST /auth/review-login` 3,731 ms for an existing user (bcrypt is not called on that path — worth a look); `/api/googlebooks/search` depends on Google, not us.
