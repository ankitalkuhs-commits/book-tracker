## How to read this plan

- The plan is **split by the PM's halves** (E-5): **Part A — Report** (sections 2–4) is independently shippable and moves no query budget; **Part B — Block** (sections 5–9) follows. Within each half the cases are grouped by the architecture's work packages. A Builder reads section 0, section 1, their own section, and the gates.
- **Ids.** The architecture's ids are kept where they exist: `S-01..S-16` (report API), `B-01..B-08` (block semantics), `B-10..B-36` (serving paths, the helper, coverage), `B-40..B-44` (budgets), `C-01..C-10` (clients). New ones continue each series (`S-17`, `B-37`, `C-11`) or take a letter suffix (`B-13a`, `C-04m` for the mobile twin of a web case). Production checks are renumbered `P-4I-01..` so they do not collide with 4C/4F/4G's in the run ledger. Other prefixes: `ST-4I` static command from the worktree root · `RG-4I` regression · `G-4I` gate · `D-4I` a device check a human performs · `MUT-4I` a row of the mutation table (section 13).
- **Severity.** **Critical** = a block leaks on any path, a report is lost or unseen, a refusal lands after a row or a notification, a block opens a private profile, a cascade leaves a block pointing at a dead id. **Major** = a surface has no affordance, a budget is wrong, a bounded decision is unpinned. **Minor** = cosmetic or defensive. **Every serving-path case is Critical and is never downgraded**, because the reader cannot detect the failure it guards.
- **Priority.** P0 ship blocker · P1 fix within the sprint · P2 nice to have.
- **Mutation testing is the acceptance rule.** Every case names the **one-line change to named product code** that must turn it red, and the first failure line to expect. **A case whose mutation stays green is not coverage: the merge is blocked until the test is fixed or the case is deleted.** Ideas for which no mutation could be named do not appear here — that is why four of the architecture's draft rows have been split (B-14/B-14a, B-15/B-15u, B-32/B-32a, C-04/C-04m) and three moved out of the automated suite into section 11.
- **This sprint's single most important mutation is `MUT-4I-30`: transposing one `or_` arm in `app/blocks.py`.** It ships a block that works in one direction and passes a smoke test. Every serving-path parameter therefore runs **in both directions** and the parametrisation asserts its own length first.
- **"Expected" is what spec.md and pm-decisions.md promise as amended by section 0**, not what the code does today.
- Where a case says "unchanged", the assertion is against a **captured before value**, never a literal typed into the test (4E's section 2.5 rule).

### Non-vacuity rules — carried forward from 4C/4F/4G, extended for 4I

Binding on every case. Rules 1–8 are 4F/4G's. Rules 9–16 are this sprint's, each for a defect this project has actually shipped.

1. **Every injection asserts a control.** A test that blocks a reader also exercises an unblocked reader in the same response.
2. **Every enumeration first proves its inventory is complete.** A parametrised walk asserts the list it walks **equals** the full set discovered from `app.routes` / the file, before it checks anything.
3. **Every detector runs against a synthetic negative.** A rule that greps, walks an AST, scans a diff or classifies routes proves on a deliberately-failing input that it reports a hit, in the same test.
4. **A walker that finds zero sites fails.** Every enumerating test asserts `found == EXPECTED_N` against a literal written out in this plan, **before** the per-site assertions.
5. **Every new test file opens with an import guard at module scope**, so a missing or renamed symbol is one loud collection error and never N silent skips.
6. **No gate counts a `-k` filter's output.** Mutation rows name a test by its **full node id**, never a substring.
7. **A file that fails to load is a count change, not one failure.** Gates compare collected / `# tests` / `# pass` / `# fail` **exactly**. *(The defect: a stray newline made a test file unparseable and the suite silently dropped 16 tests.)*
8. **A test that can pass against unbuilt code is a defect.** Every case names the symbol whose absence must make it fail loudly rather than skip (K-4I-07).
9. **Every serving-path case runs in BOTH directions**, as two parameters of one parametrisation whose length is asserted (`len(DIRECTIONS) == 2`). A one-directional suite cannot tell a symmetric block from a transposed `or_` arm. *(MUT-4I-30.)*
10. **Every "absent" assertion is paired with a "present" assertion about a third, unrelated reader in the same response.** Without it, a filter that returns `[]` for everybody passes every case.
11. **A 404 case asserts the response **body**, byte-identical to the deleted-account 404** — not merely the status. A block that 403s, or that 404s with its own message, is distinguishable and fails R-20's asymmetric-control clause.
12. **No test reaches a state by planting a row that a real request can reach.** Blocks are created by `POST /blocks/{id}`, or B-01's unfollow is uncovered. The two deliberate exceptions are named in their own rows: B-12 plants a `follow` row *to defeat* R-21, and the budget seed plants `block` rows because it is not a semantics test (B-43a asserts the seed's own invariants).
13. **A rule that bans a pattern runs over EVERY file that could hold it, and asserts the file count first.** *(The defect: a rule banning a pattern checked one file while an identical bug sat in six others.)* B-35a walks all of `app/`, asserts it saw ≥ 25 files, and then asserts the violation list is empty.
14. **A detector may not assert "at most one" of a required thing.** Every inventory asserts an exact count, so deleting the thing entirely fails. *(The defect: a detector asserted "at most one" and deleting the subject passed.)*
15. **Every diff-based case asserts its diff range is non-empty before parsing it.** *(The defect: a guard's range was empty after a merge and three cases asserted nothing.)*
16. **A test must not be able to pass because of the host OS.** Nothing in this sprint is clock- or locale-dependent, and the one place a platform could answer the question for us — a `NOT IN ()` warning on an empty set — is asserted with `warnings.catch_warnings(record=True)` and a positive control, not by trusting that no warning appeared (B-35b). *(The defect: a timezone test passed on Windows for the wrong reason while Linux had the bug.)*

## 15. What this plan does NOT cover

Stated plainly, because a gap nobody names becomes a gap somebody assumes was covered.

1. **Nothing proves App Review accepts this as satisfying Guideline 1.2.** It is a human judgement on a submission and it is binary. **Substitute proof:** the four-row table at the top of spec.md pasted into the submission notes with the exact in-app path to Report and to Block, plus D-4I-01, D-4I-02 and D-4I-04's screenshots. No CI substitute exists and this plan does not invent one.
2. **"Timely responses" is an operational commitment, not code.** The admin notification (S-12) and the queue (S-10) are the code half and are tested. The **2 working days** of pm-decisions E-3 is a promise a person keeps; nothing in CI can assert it, and a queue with no owner is not a mechanism.
3. **A block that leaks on a path nobody enumerated is still possible — but only for one commit.** B-32 is the control, and its honest scope is this: it proves every route is **classified**, and B-32a proves the sentinel does not appear on the reachable unfiltered GETs. It does **not** prove that a route classified `NOT_SERVING` is correctly classified; a wrong classification with a plausible reason string passes. **What makes that acceptable:** the classification is a diff a reviewer must approve, and the reason is required to be there to approve. That is a review control, not a test control, and it is the weakest link in this design.
4. **Non-GET routes are classified but not probed.** B-32a's sweep is GET-only, because driving 57 non-GET routes with a blocked pair means writing 57 payloads and tolerating their side effects. The five existing refusals are covered behaviourally (B-05, B-15, B-15u, B-27) and the rest are classified. **A write route that leaks another reader's name in its RESPONSE would not be caught** — e.g. if `POST /groups/{id}/posts` ever echoed the circle's member list.
5. **No concurrency and no PostgreSQL in the automated suite.** S-03 and B-02 assert that a duplicate produces one row and a deterministic status against **SQLite's** unique-index `IntegrityError`, not two simultaneous requests against PostgreSQL. 4C built `qa/pg_4c_migration.py` for exactly this gap; extending it is a half-day and this sprint does not. P-4I-02, P-4I-03 and P-4I-07 are the only proof the production indexes exist and bite.
6. **`DELETE /notes/{id}/like`'s missing visibility check is not fixed** (K-4I-04). B-15u adds a **block** check only. A stranger can still send a 200-returning unlike for a private note they cannot see. It predates this sprint, it leaks nothing, and it is logged for triage rather than fixed inside a safety sprint's diff.
7. **A blocked reader's second account is not stopped** (F2). A block is between two `user` rows. Nothing here claims otherwise and no test pretends to.
8. **The anonymous feed is unfiltered and that is asserted, not fixed** (E-8, B-11). A blocked reader who signs out reads the blocker's public posts. The only existing control is `is_private_profile`. The UI copy says so (C-06's third anchor) and that is the whole mitigation.
9. **The circle residual is asserted as correct** (E-2, B-26). A reader who blocks someone in their book club still sees that person in the Members list, in the leaderboard, in the member count, in `/groups/{id}/pending` and in `/groups/invites/pending` (K-4I-05). B-26 and B-32a make a future "fix" fail, which means this plan actively defends a behaviour readers may report as a bug.
10. **A report about the admin is reviewed by the admin** (E-6). No code change can fix it and no test is written for it. There is one admin address (`admin_router.py:350`).
11. **The clients are proved as source shape only.** Every C-* case is an AST or anchored-text assertion over committed source: it proves a Report item exists at each site, outside a closed gate, with owner-only actions still guarded. It does **not** prove the item renders, that the touch target is reachable, that the modal opens, or that the request is sent. **Substitute proof:** D-4I-01, D-4I-02, D-4I-04 and P-4I-09, by hand, on both builds. The mobile touch target is covered by the existing `__tests__/a11yTouchables.test.mjs` pattern only if the new controls are `TouchableOpacity`/`Pressable` — if P5 reaches for a different primitive, that sweep silently stops seeing them, exactly as 4G's K-17 found for `AppleAuthenticationButton`.
12. **Push suppression is proved in-process, not end to end** (B-29). `send_expo_push` and `send_web_push` are monkeypatched in every case. Expo and Web Push are external; P-4I-12 is the one live run with two review accounts.
13. **The PM SQL is proved as text, not as an executed migration.** S-23 and B-53 parse `context/PM_SQL_QUEUE.md`. They cannot prove the PM ran it, that PostgreSQL accepted it, or that `CREATE UNIQUE INDEX IF NOT EXISTS` was not skipped against a pre-existing non-unique index of the same name. G-4I-08, G-4I-09, P-4I-02 and P-4I-03 are the only proof and they are the PM's output, pasted back.
