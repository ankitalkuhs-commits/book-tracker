## Contracts that must not drift

### Userbook shape  ⚠️ 13 consuming files
Returned by `GET /userbooks/`, `GET /userbooks/{id}`, `GET /userbooks/user/{id}`, `POST /books/add-to-library`. Flat object with a nested `book` that **must include `google_books_id`** (duplicate detection in BookPreviewScreen / BookPreviewModal keys on it):
```
{ id, user_id, book_id, status, current_page, rating, format, ownership_status, created_at, updated_at,
  book: { id, title, author, description, total_pages, cover_url, google_books_id } }
```
`PUT /userbooks/{id}/progress` and `PATCH /userbooks/{id}` return minimal dicts `{id, status, current_page, rating, updated_at[, book_total_pages]}` — never a raw SQLModel.

Why: on 2026-05-04 `add-to-library` returned `{message, book, userbook}`, BookPreviewScreen stored the wrapper → `PATCH /userbooks/undefined` 422. Same day, `handleRating` used PUT /progress with `{rating}` → `current_page=0` → every rated book reset to `to-read`. **Rating goes through PATCH; page progress through PUT.**

### `GET /profile/me`  ⚠️ 10 consuming files
`stats` carries both snake_case and camelCase keys (`total_books`/`totalBooks`, `to_read`/`toRead`, `total_pages_read`/`totalPagesRead`) on purpose — mobile reads camel, web reads snake; removing either breaks a shipped app build. `GET /profile/{id}` returns `stats: null, locked: true` for a private profile the caller does not follow; `follows_you` + `yearly_goal` were added 2026-05-04 for the Follow-Back label.

### Note card shape — `GET /notes/feed`, `/friends-feed`, `/me`, `/user/{id}`
`{id, user_id, text, emotion, quote, image_url, is_public, created_at(Z), likes_count, comments_count, liked_by_me, user_has_liked, user:{id,name,username,profile_picture}, book:{id,title,author,cover_url}}`. `liked_by_me` and `user_has_liked` are duplicates kept for old clients. The community feed excludes `is_private_profile` authors in `crud.get_notes_feed`.

### `app/deps.py :: get_current_user`
Every authenticated route. Also writes `user.last_active` once per day — the streak-reminder scheduler reads it. Changing this touches every request and the reminder logic.

### Auth / review — `POST /auth/review-login` + `GET /version`  (added 2026-09-13)
Both routes are auth-level `NONE` in the generated table and carry ⚠️. That is correct and deliberate, not a gap.

`POST /auth/review-login` is **gated by an env allowlist + a shared secret, and returns 404 when unconfigured** — with `REVIEW_LOGIN_SECRET` or `REVIEW_LOGIN_EMAILS` unset it behaves as if the route does not exist, which is the state of local dev, the test suite, and any fork. When configured, it accepts only addresses that are in `REVIEW_LOGIN_EMAILS` (comma-separated, trimmed, matched case-insensitively) **and** end in `@trackmyread.com`; everything else gets an identical 401, so the response cannot be used to enumerate the allowlist. The secret is compared with `hmac.compare_digest`. It returns the **same body as `POST /auth/google`** — `{access_token, is_new, user:{id,name,email}}` — and creates the account the same way (`secrets.token_urlsafe(32)` → `auth.hash_password` → `crud.create_user`), so review accounts are ordinary users and every downstream contract (`get_current_user`, `/profile/me`, the note-card shape) applies to them unchanged. No client calls it; the token is used by `curl`, by `scripts/seed_review_accounts.py`, and by pasting it into `localStorage.bt_token` for web screenshots. Both env vars are read **inside the request**, never at import time — a module-level read would freeze the value at test-collection time and make `monkeypatch` useless.

`GET /version` returns exactly `{commit, service, branch}` from `RENDER_GIT_COMMIT` / `RENDER_SERVICE_NAME` / `RENDER_GIT_BRANCH`, all `null` off Render. Unauthenticated on purpose: it is how a deploy is confirmed in one curl, which must not depend on login working (sprint 2's deploy could not be confirmed at all). **Never add anything else to this response** — it is the one endpoint with no auth and no rate limit, so it must never read a secret, a database row, or `os.environ` wholesale.

`/version` lives in `app/routers/meta_router.py` with **no `prefix=` argument**, not in `main.py`. `scripts/gen_dependency_map.py` only matches `@router.<verb>(`, so an `@app.get()` route in `main.py` is invisible to the map — which is why `GET /` has never appeared in it. Keep `/version` in a router. See `features/auth/review-login/decisions/ADR-001-version-route-placement.md`.

### `app/notifications/dispatcher.py :: fire_event()` + `config.py`
The only push path (Expo + web push + NotificationLog). Callers: follow_router, likes_comments, books_router, userbooks_router (×3), groups_router (invite, join request, approve/reject), notifications/router (admin test), `notifications/scheduler.py` (`reading_streak_reminder`, `actor_id=0`, added sprint-2).

One deliberate exception: `admin_router.broadcast_push_notification` fires `event_type="admin_broadcast"` by calling `send_expo_push` + `send_web_push` per user and writing its own `NotificationLog` row (`actor_id=<admin id>`). It bypasses `fire_event` because the admin supplies `title`/`body` at call time (nothing to template) and an operational announcement is **not** gated on per-user prefs — `admin_broadcast` is therefore absent from `USER_PREF_KEYS`. It is registered in `config.py` so the admin events screen can list and kill-switch it; only `is_active` is honoured.

Pref keys shared with both Settings screens: `new_follower · post_liked · post_commented · book_completed · reading_streak_reminder · group_invite · group_join_request` (`book_added` follows `book_completed`).

Template trap: `_render_template` returns the raw template on a missing `{placeholder}` — no error. Every `extra` must supply every placeholder in the config entry.

### `pushtoken` table
One table, two channels: `token_type='expo'` (mobile) and `'web'` (PWA). `push_router.py` register and deregister both filter `user_id` AND `token_type == "expo"`, so a mobile login or logout never touches a user's web-push row. Any query on this table must filter `token_type`.

### `reading_activity` table
Written only by `PUT /userbooks/{id}/progress` (upsert per userbook per UTC day). Read by `/reading-activity/daily`, `/insights`, `/user/{id}/daily`, and `GET /groups/{id}/leaderboard` + `/goal`. Changing the write (e.g. logging on PATCH too) changes all four readers.

### `context/supabase_migration.sql` ↔ `app/models.py`
Every column in models.py must have an `ADD COLUMN IF NOT EXISTS` here and be run in Supabase **before** the model ships. Pushing first crashes every query on that table (April 2026 login outage).

### Mobile `App.js :: preloadData()` → PreloadContext
Keys `profile, library, feed, insights, activity, notes, groups, pendingGroups` seed the Feed / Library / Insights / Groups / Profile screens. Adding a screen that should open instantly means adding a request here; changing a response shape here changes the first render of every tab.

### Web `src/services/api.js` cache
60s GET cache, stale-while-revalidate. Mutations must call `cacheClear(prefix)` for `/userbooks`, `/notes`, `/profile` as appropriate or the UI shows stale data for up to a minute.

### `googlebooks_router.normalize_google_cover_url`
Imported by `userbooks_router` — cover URLs are normalised on read, not on write. `GET /api/googlebooks/search` is **unauthenticated**; both clients map `google_id → google_books_id`, `authors[] → author`, `isbn_13|isbn_10 → isbn` client-side.

### Onboarding / tour keys
Web `ONBOARDING_KEY = 'bt_onboarding_v1'` (OnboardingPage.jsx; read in App.jsx + LoginPage). Mobile `TOUR_KEY` (AppTour.js; read in App.js). Bump to force a re-tour for everyone.

## Parity gaps visible from the map (2026-09-12)
- Mobile never calls `GET /notes/friends-feed` or `GET /groups/invites/pending` — no Friends tab and no curator-invites list on mobile.
- Web never calls `GET /groups/{id}/activity` — the group activity feed is mobile-only.
- Web `demoLogin → /auth/demo-login` and mobile `userAPI.getUser → /users/{id}` hit routes that do not exist.
- Mobile push registration bypasses `api.js` (`NotificationService.js` has its own base URL + fetch), so `userAPI.registerPushToken` is dead.
