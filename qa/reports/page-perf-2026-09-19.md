## Analysis — why signed-in pages are slow (2026-09-20)

**Public pages are fast:** 0.26–0.39 s ready on desktop and ~1.8 s on a throttled phone, with LCP 2.2–2.5 s, at Google's "good" line. **Signed-in pages take 2.9–6.4 s on desktop and 3.6–8.9 s on a phone.** A return visit is barely faster than a first visit, so the time goes to waiting on the API, not to downloading the app.

### 1. Every database query costs ~180 ms (infrastructure)
Median time to first byte on production, 7 samples each, against locally counted SQL statements per request:

| endpoint | queries | TTFB |
|---|---:|---:|
| `/version` | 0 | 0.30 s |
| `/notifications/unread-count` | 2 | 0.99 s |
| `/userbooks/` | 3 | 1.19 s |
| `/profile/me` | 5 | 1.53 s |
| `/notes/feed` | 8 | 2.09 s |
| `/books/recommendations` | 12 | 2.75 s |

Time grows linearly with query count: **~0.18 s per query** from 2 to 12 queries. A query to a database in the same region takes 1–2 ms, so this is a cross-region round trip between Render (API) and Supabase (database). The regions are only visible in the two dashboards. Co-locating them is the largest single speed-up available and needs no code change. **F-68.**

### 2. Every signed-in page waits on `/profile/me` first (web code)
Waterfall on production, milliseconds from navigation:
```
/home
    298 →  1833  /profile/me                 <- nothing else starts until this returns
   1917 →  5301  6 page calls in parallel     (slowest: /notes/feed)
/groups/7
    312 →  2205  /profile/me
   2231 →  3541  /groups/7                    <- a second wait
   3547 →  6474  members, leaderboard, goal, posts, activity (need only the id in the URL)
```
Every signed-in page pays the `/profile/me` round trip (1.5–1.9 s) in series, on every load. **F-69.** The circle page adds a second serial stage it doesn't need. **F-70.**

### 3. 4A's feed fix is live
`/notes/feed` was **9.2 s and 114 queries** for 50 notes before 4A (F-08). It is now **8 queries and ~2.1 s** by itself, and what remains of that time is F-68's per-query cost.

### Expected effect of the fixes (estimates, to be measured)
- **F-68 alone:** per-query cost ~180 ms → a few ms, so `/profile/me` ~1.5 s → ~0.35 s and the feed ~2.1 s → ~0.35 s. Most signed-in pages would land near 1–1.5 s on desktop.
- **F-69 + F-70 alone:** remove one serial stage from every page (~1.5 s) and a second from the circle page (~1.3 s). Circle page 6.4 s → ~3.5 s, home 5.4 s → ~3.7 s.

## Measured inside the server — Server-Timing (2026-09-20, commit 87664e7)

Median of 5 samples per endpoint on production:

| endpoint | queries | DB time | **per query** | server total | client total |
|---|---:|---:|---:|---:|---:|
| `/version` | 0 | 0 ms | – | 1 ms | 294 ms |
| `/notifications/unread-count` | 2 | 503 ms | **251 ms** | 674 ms | 970 ms |
| `/userbooks/` | 3 | 670 ms | **223 ms** | 843 ms | 1133 ms |
| `/profile/me` | 5 | 1005 ms | **201 ms** | 1182 ms | 1464 ms |
| `/notes/feed` | 8 | 1510 ms | **189 ms** | 1712 ms | 2018 ms |
| `/books/recommendations` | 12 | 2185 ms | **182 ms** | 2364 ms | 2657 ms |

What this proves:
- **Each query spends ~180–250 ms in the database.** These are trivial primary-key and count queries that execute in about a millisecond, so this is network round-trip time from the API server to the database. F-68 is confirmed by direct measurement rather than inferred.
- **Every request pays one more hidden round trip** (~175 ms) that the query counter doesn't see: server total minus DB time is ~170–200 ms on every endpoint. It is `pool_pre_ping=True`, a `SELECT 1` on connection checkout. Keep it (the research brief recommends it). Its cost falls to ~1–2 ms once the API server and the database share a region.
- **Reader to API server costs ~290 ms** for a request that does no work (`/version`, 1 ms in the server).
- **The application code itself costs a few milliseconds.** It is not the bottleneck.

**Not visible in any of the above: Render free-tier sleep (F-73).** Render spins a free service down after 15 minutes without traffic, and waking takes about a minute (Render docs; `qa/research/web-performance-2026-09.md`). These measurements woke the API first on purpose, so they exclude it. A reader who arrives after a quiet spell can wait up to a minute. The Starter plan ($7/month, 0.5 CPU against the free tier's 0.1) removes it.
