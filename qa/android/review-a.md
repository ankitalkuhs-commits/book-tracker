# Android Mobile Code Review A — TrackMyRead

Scope: `App.js`, `index.js`, `app.json`, `src/navigation/AppNavigator.js`, `src/services/api.js`, `src/services/NotificationService.js`, `src/context/NotificationContext.js`, `src/components/AppHeader.js`, `src/components/AppTour.js`, `src/screens/{LoginScreen,OnboardingScreen,FeedScreen,SearchScreen,BookPreviewScreen,BookDetailScreen,LibraryScreen}.js`, `src/utils/bookUtils.js`, `src/buildInfo.js`. Every file read in full. All findings below were verified by reading the corresponding backend router; nothing here is guessed.

Companion inventory: `qa/inventory/mobile-a.json` (73 actionable elements).

---

## Critical

1. **Push notifications silently stop working for the second account on a shared device — device-token guard is never reset.** `NotificationService.js:13-14` keeps `lastRegisteredExpoToken` as a **module-level** variable. `App.js:159-162` re-runs `registerExpoPushToken` whenever `isLoggedIn` flips to `true`, but the guard inside `registerExpoPushToken` (`NotificationService.js:62`) compares against the raw Expo device token, which is device-bound, not account-bound. Sequence: User A logs in → token `T` registered under A's account → `lastRegisteredExpoToken = T`. User A logs out (token cleared client-side, but see #2 — the backend row is never removed either). User B logs in on the same device → the effect fires again → `Notifications.getExpoPushTokenAsync()` returns the **same** device token `T` → the guard sees `lastRegisteredExpoToken === T` and returns **without calling `POST /push-tokens/`** for User B. User B receives zero push notifications until the app is force-killed and relaunched (which resets the module variable). Failure scenario: two people share a phone (common on Android in India/family accounts); the second person never gets a single like/comment/follow notification and has no way to know why.

2. **Onboarding's "add a book" step is completely non-functional.** `AppTour.js:187` — `setBookResults((res.books || res || []).slice(0, 5))`. `GET /api/googlebooks/search` returns `{results, total_items, query_used, has_more, next_start_index}` (`app/routers/googlebooks_router.py:185-193`); there is no `books` field. `res.books || res` therefore evaluates to the response **object**, and `.slice()` throws `TypeError: res.slice is not a function`. The throw is caught by the surrounding `try/catch` (`catch { setBookResults([]) }`), so no crash occurs — but the tour's book-search step returns zero results for every query, forever. Failure scenario: every new user who reaches the "add your first book" step of the guided tour sees "no results" no matter what they type, and can never complete that step normally (only Skip works).

3. **No global handling of an expired/invalid session — the app can end up "logged in" with a dead token and no way back to Login.** `api.js:24-31`'s response interceptor does `AsyncStorage.removeItem('bt_token')` on any 401 but never notifies the rest of the app (no event, no forced `isLoggedIn=false`, no navigation to Login). `App.js:76-87`'s mount effect calls `authAPI.isLoggedIn()` (checks only *presence* of a token, not validity), then unconditionally `awaits preloadData()` (`App.js:90-118`, `Promise.allSettled` — a 401 on every one of the 9 calls just becomes a "fulfilled-with-fallback" result) and then unconditionally sets `isLoggedIn(true)`. Failure scenario: a user reopens the app after their JWT has expired (or after a backend-side forced logout) and lands on a fully-rendered but completely empty Feed/Library/Insights with no error message and no way to re-authenticate short of manually finding Settings → Sign Out (whose contents are also empty, since profile never loaded).

## High

4. **Adding a book discovered via Feed/Recommendations/Friends-Reading can create a duplicate `Book` catalog row instead of reusing the existing one.** `POST /books/add-to-library` (`app/routers/books_router.py:35-96`) can only match an existing `Book` by `google_books_id` or `isbn` — there is no `book_id` field on `AddBookFromGooglePayload` at all. But three call sites hand it books that only carry the **local** `Book.id`, never a Google id:
   - `GET /books/recommendations` items are `{id, title, author, cover_url, total_pages, description, reason, friend_name}` (`books_router.py:295-303`) — no `google_books_id`.
   - `GET /userbooks/friends/currently-reading` nested `book` is `{id, title, author, cover_url, total_pages}` (`userbooks_router.py` ~547) — no `google_books_id`.
   - `GET /notes/feed` nested `book` is `{id, title, author, cover_url}` (`notes_router.py` `get_feed`) — no `google_books_id`.
   `BookPreviewScreen.js:66-73` (`handleAdd`) and `FeedScreen.js`'s dead shelf-modal handler both send `google_books_id: book.google_books_id || book.google_id || null`, which is `null` for all three sources above, and never fall back to the local `book.id` (which the response *did* provide). Result: `add_book_to_library` can't find the existing row, creates a new `Book` with the same title/author, and the user's library entry points at the duplicate. Failure scenario: user taps a book from a friend's "currently reading" card or a "For You" recommendation and adds it — the catalog now has two rows for the same book, recommendations/search results degrade over time, and cross-referencing (e.g. "who else is reading this") silently splits between the two rows.

5. **Logout never deregisters the Expo push token from the backend.** `NotificationService.js:88-102` exports `deregisterPushToken`, and it is **never called from anywhere** (`grep -rn "deregisterPushToken"` across the whole mobile source returns only its own definition). `ProfileScreen.js:394` and `SettingsScreen.js:288/297` call `authAPI.logout()` (clears the local JWT) and `onLogout?.()`, but neither calls `deregisterPushToken`. Combined with #1's stale device-token guard, a former account keeps its `PushToken` row (`token_type='expo'`) on the backend indefinitely after the user signs out locally. Failure scenario: on a shared/borrowed/resold device, the previous account keeps silently receiving push notifications (likes, comments, follows) for events on their account, revealing social activity to whoever now holds the device, until they separately go delete the account or the token naturally goes stale.

6. **Render free-tier cold start (~30s) races the shared axios timeout (also 30s).** `api.js:8-12` sets `timeout: 30000` on the single shared axios instance used for **every** call, including `authAPI.googleLogin` (Google sign-in) and all 9 of `preloadData`'s parallel requests. `context/LOAD_ME_FIRST.md` documents the backend can take ~30s to wake from Render's free-tier sleep. A request issued right as the server is waking has a real chance of hitting the 30000ms ceiling and aborting (`ECONNABORTED`) with no retry anywhere in `api.js`. Failure scenario: the very first thing a returning user does after the app has been idle 15+ minutes is tap "Continue with Google" or sit through the post-login preload — either can time out silently (Alert shown for login failure, but preload failures are swallowed into empty preloaded state, see #3's failure mode).

7. **Two entire screens are dead code, unreachable from the app's navigator, and have latent bugs of their own.** `grep -rn "SearchScreen\|OnboardingScreen"` across `src/navigation/AppNavigator.js` and `App.js` returns no references to either component being rendered anywhere — only their own `export default function ...` declarations. `dependency-map.md`'s auto-generated table still lists both as consumers of `/api/googlebooks/search` etc. because it's a static grep of source, not a reachability check — see the Dependency refinement table below.
   - `SearchScreen.js`'s `confirmAdd` (line 224-241) never sends `google_books_id` at all (unlike `LibraryScreen.js`'s sibling `AddBookModal.addBook`, which correctly sends `google_books_id: selectedBook.google_id`), so if this screen is ever reconnected, books added through it will always land with `google_books_id=null`.
   - `OnboardingScreen.js`'s `searchBooks` (line 102-110) has the same `res?.items || res` bug class as finding #2.
   These are pure maintenance risk today (no live impact since unreachable) but will bite silently the moment someone re-wires a "Search" tab or restores first-run onboarding without re-auditing them.

## Medium

8. **Community feed has no virtualization.** `FeedScreen.js:805-817` renders the whole post list inside a `ScrollView` with `posts.filter(...).map(renderPost)` rather than a `FlatList`. Every post card (up to the 50-item `/notes/feed` limit), including any embedded images, mounts simultaneously. This will show up as scroll jank/memory pressure on lower-end Android devices as the feed grows, and contradicts the FlatList-based patterns used elsewhere (`LibraryScreen`, `SearchScreen`, `AddBookModal`).

9. **`preloadData()` fires 9 parallel requests plus an unconditional cover-fix loop on every login/cold start.** `App.js:90-130` — confirmed as documented in `repos/mobile/index.md`'s Health section; `_silentCoverFix()` always calls `GET /import/covers-status` and then, unconditionally, `POST /import/fix-covers-batch` in batches of 10 for every returned id, on every single app launch, with no local cache of "already checked this session." On a large library with several miscategorized covers this adds several more sequential POSTs after the initial 9-way fan-out, all before the user reaches an interactive screen.

10. **Inconsistent `__DEV__` gating for console logging in `NotificationService.js`.** Lines 56 (`console.error('[Push] getExpoPushTokenAsync failed:', ...)`), 74, and 98 (`console.warn('[Push] Backend ... failed:', response.status)`) are **not** wrapped in `if (__DEV__)`, while the two calls at lines 79 and 81 in the same file are. `context/LOAD_ME_FIRST.md`'s May-2026 entry documents this file as one of the ones already "fixed" to gate console output in production — these three calls are the exception that slipped through. Low sensitivity (no tokens/PII logged, just status codes and error messages) but inconsistent with the stated convention.

11. **Star-rating rollback in `BookDetailScreen` is a no-op.** `BookDetailScreen.js:162-166` — `handleRating` does `setRating(stars)` optimistically, and on failure does `catch { setRating(rating) }`. By the time the catch runs, the closed-over `rating` variable is still the **old** state value only if `setRating(stars)` hasn't triggered a re-render yet — in practice React batches this such that `rating` here is captured at the time `handleRating` was invoked (i.e., the *previous* value), so this usually does work by accident of closure timing, but it's fragile: if this function is ever refactored to read `rating` from a ref or if React's batching semantics change (e.g. under automatic batching edge cases), the "rollback" will re-apply the same optimistic value instead of the true previous one. Recommend rewriting as `setRating(prevValue)` captured explicitly before the optimistic update, not relying on closure timing.

12. **Per-book reflections default to public with no toggle.** `BookDetailScreen.js:172` (`handleAddNote`) calls `notesAPI.createNote({ userbook_id, text, quote })` without `is_public`. `NoteCreateSchema.is_public` defaults to `True` server-side (`notes_router.py`). This composer is presented purely as a book-level "reflection" (no privacy control shown anywhere on this screen), yet it publishes to the public community feed by default — unlike `FeedScreen`'s composer, which explicitly and intentionally sets `is_public: true`. Likely unintended given the private-journal framing of this UI.

13. **JWT stored in plain `AsyncStorage`, not `expo-secure-store`.** `api.js` (`authAPI`) and every other read of `bt_token` use `@react-native-async-storage/async-storage`, which is unencrypted on Android (backed by a plain SQLite/file store within the app sandbox). A session token with the lifetime seen here (no visible short-expiry/refresh flow in these files) is more sensitive than typical AsyncStorage content; recommend `expo-secure-store` (Android Keystore-backed) for `bt_token`.

14. **Friend-reading avatars never render a real photo.** `GET /userbooks/friends/currently-reading`'s nested `user` object is `{id, username, name, is_mutual}` only (`userbooks_router.py` ~547) — no `profile_picture`. `FeedScreen.js:524` reads `item.user?.profile_picture`, which is always `undefined`, so the Friends tab's "currently reading" cards always show initials, never the friend's actual photo, even though the same friend's photo shows correctly everywhere else (feed posts, search results) that use a different endpoint.

15. **The two "Add Book" UIs disagree on allowed `format` values.** `LibraryScreen.js`'s `AddBookModal` offers `kindle` as a format chip (`LibraryScreen.js:427`); `SearchScreen.js`'s `FORMAT_KEYS` (dead code, but documents the intended set) is `hardcover/paperback/ebook/audiobook` — no `kindle`. `AddBookFromGooglePayload.format` is an unvalidated free string server-side so this doesn't error, but it's a schema/UX inconsistency between the app's two book-adding flows.

16. **`KeyboardAvoidingView` is explicitly a no-op on Android in the one place it's used.** `LibraryScreen.js:296` — `behavior={Platform.OS === 'ios' ? 'padding' : undefined}` inside the `AddBookModal`'s `pageSheet` modal. On Android this renders with no keyboard-avoidance behavior at all, relying entirely on the OS's default resize behavior. Combined with `app.json`'s `edgeToEdgeEnabled: true` (Android 15 edge-to-edge, new in this Expo/RN combination), OS-level window resize-on-keyboard can behave differently than the classic (non-edge-to-edge) `adjustResize`; worth an on-device check that the search input and status/format chip rows in this modal aren't obscured by the keyboard on Android 15 devices.

## Low

17. **No unmount guards on async screen loaders.** None of `FeedScreen`, `LibraryScreen`, `BookDetailScreen`, or `BookPreviewScreen`'s data-loading functions (`loadFeed`, `loadBooks`, `loadNotes`, the `getMyBooks` effect, etc.) check whether the component is still mounted before calling `setState` in their `.then`/`finally` blocks. Not a hard crash on modern React Native, but will produce "Can't perform a React state update on an unmounted component" warnings if a user navigates away while a request is in flight.

18. **Unhandled promise rejection possible in `AppTour.finish()`.** `AppTour.js:172-177` passes an `async` callback into `Animated.timing(...).start(callback)`. If `AsyncStorage.setItem(TOUR_KEY, '1')` throws, the rejection is unhandled and `onDone?.()` is never called, leaving the tour's transparent modal stuck on screen with no way to dismiss it (Skip/Next both funnel through `finish()`).

19. **`Linking.openURL` calls have no `.catch()`.** `BookPreviewScreen.js:120` and `BookDetailScreen.js:267` both call `Linking.openURL(getAmazonUrl(...))` directly in an `onPress` with no error handling. Unlikely to fail on a stock Android device (a browser is always available), but on a locked-down/enterprise device with no browser it becomes an unhandled promise rejection with no user feedback ("Buy on Amazon" would appear to do nothing).

20. **`newArchEnabled: false` on Expo SDK 54 / RN 0.81.** `app.json:9`. Expo SDK 54 defaults to the New Architecture (Fabric/TurboModules) on; this app explicitly opts out. Given Expo's stated direction of eventually requiring the New Architecture, this is a version/dependency risk worth a deliberate revisit rather than an indefinite opt-out — confirm which dependency (if any) still forces the legacy architecture.

21. **No cover-image fallback in `AddBookModal`'s search results.** `LibraryScreen.js:340-344` renders `<Image source={{uri: item.cover_url}}>` with no placeholder/`onError` handling, unlike `SearchScreen.js`'s `BookCard` (which shows a book-outline icon when `cover_url` is falsy or the image errors). A book with no cover shows a blank box in this modal.

22. **Post overflow menu (`···`) has no outside-tap dismiss.** `FeedScreen.js:637-651`. Once opened, the Delete dropdown stays open until the same button is tapped again; tapping Like, Comment, or scrolling doesn't close it. Minor UX rough edge, not a functional bug.

23. **`expo-image-picker` is used (`FeedScreen.js`) but not listed in `app.json`'s `plugins` array.** Unverified whether this matters: recent Expo SDKs auto-apply a library's bundled config plugin during prebuild even when it isn't explicitly listed, so this may be a non-issue — flagging for an on-device/EAS-build check rather than asserting a bug, since I could not confirm the prebuild output from source alone.

## Verified clean (explicitly checked, no issue found)

- `adjustsFontSizeToFit` — absent everywhere in scope, correctly following the project's own gotcha list.
- Font-loading invisibility — `App.js` gates the entire app behind `fontsLoaded && authChecked` and keeps the native splash screen up until then; no flash-of-unstyled-text window.
- `Alert.prompt` — not used anywhere; `BookDetailScreen`'s "unknown total pages" flow correctly uses a real `Modal` + `TextInput` instead, per the project's iOS-only-`Alert.prompt` gotcha.
- Rating vs. progress endpoint split (the May 2026 regression) — `BookDetailScreen.js` correctly uses `patchUserbook` (PATCH) for `handleRating` and `updateProgress` (PUT) for `handleSaveProgress`. No regression found.
- `add-to-library` flat response shape — `BookPreviewScreen.js` correctly stores the flat result directly (`setMyUserbook(result)`), no `.userbook` unwrap. No regression found.
- `push-tokens` `token_type` filtering (sprint-1 fix) — `push_router.py` filters by `token_type == "expo"` on both register and deregister; `NotificationService.js`'s direct fetch calls match this contract.
- `GET /profile/me` snake_case/camelCase dual stats keys — present and intact; not consumed directly by any file in this scope, but confirmed unbroken.
